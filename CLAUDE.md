# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OnBeat is a PWA for band rehearsal. Each member opens a shared 6-digit room on their own phone and picks a part (guitar1 / guitar2 / bass / drums / keys). Any member can start or stop, and every device shows the same bar and beat, all driven by one shared clock. `SPEC.md` (written in Chinese) is the source of truth for scope, the sync model, the song format and the milestones. Read it before starting a milestone.

Milestones: M1 sync core → M2 score display → M2.5 metronome + drum machine → M3 rehearsal controls → M3.9 deploy + private song library (Cloudflare Worker/Durable Object/R2, library-key links; see SPEC) → M4 白玉米谱 charts (M4a: degree chords on beat slots, letter/degree display + capo, meter changes, key changes; M4b: jianpu melody + lyrics drawn in HTML/SVG, PDF import skill; then a real rehearsal decides what comes next) → M4.5 decided after that rehearsal (editor, per-instrument notation, alphaTab, GP attachments) → M5 later. The goal of M4 is "nobody gets lost in rehearsal", not a notation app. Status: M1 through M3 have passed phone testing (LAN RTT is about 7–9ms). M3.9 is built: library interface, room split, Worker + Durable Objects, R2 libraries with key links and QR, CI deploy, the library repo's R2 sync Action and in-app saving through GitHub are all live at https://onbeat.yuxuan-qi.workers.dev (RTT about 25ms; a save → commit → sync round trip was checked on 2026-10-18). Still to do: phone testing over the internet. Known bug, not yet investigated: on mobile, the "点一下屏幕开启声音" audio-unlock banner (`web/src/Room.tsx`) may misbehave.

## Commands

Node 24+, npm workspaces (`shared`, `server`, `web`, `worker`). Run everything from the repo root.

- `npm run dev`: server on :8787 (tsx watch) plus Vite on :5173. Vite proxies `/ws` to the server and listens on the LAN.
- `npm run server`: builds `web/dist`, then serves the app and `/ws` on a single port (`PORT`, default 8787). This is the rehearsal-room (LAN) mode.
- `npm run worker`: builds `web/dist`, then runs the Cloudflare Worker and Durable Objects locally with `wrangler dev` on :8788 (LAN-reachable). No Cloudflare account needed; local DO storage lives in `worker/.wrangler/` and survives restarts.
- `npm test`: runs vitest over `shared`, `server` and `worker` `src/**/*.test.ts`. Worker tests cover only `libraries.ts` (fake bucket, fake GitHub); check the Durable Object transport against `wrangler dev` with a WebSocket script.
- Single file: `npx vitest run server/src/sync.sim.test.ts`. Single test: `npx vitest run -t "late joiner"`.
- `npm run typecheck`: runs `tsc` over each package. There is no linter.

## Architecture

- `shared` is consumed as raw TypeScript (its `exports` point at `src/index.ts`). There is no build step: Vite, tsx and vitest all compile it. It holds:
  - `protocol.ts`: message types, plus `parseClientMsg`, which validates all untrusted client input.
  - `timeline.ts`: pure functions for position math and state transitions.
  - `clock.ts`: `ClockSync`, which is transport-agnostic. The browser and the server tests use the same class.
  - `song.ts`: `parseSong` validates hand-written JSON and returns a normalized copy (`{ loop, times }` sections expanded to `bars`). `compileSong(song, extraPasses)` unrolls `form` into a flat, beat-indexed timeline of bars and numbered sections ("副歌 2"). Each section gets `loopBars` × `times` from `repeatPeriod` (minimal repeating period) plus live extra passes. `songPosition` maps a beat to section, bar, chord and the next chord change. `applyDrumEdits` overlays a room's unsaved drum patterns.
- **Position is derived, never streamed.** The server broadcasts `PlaybackState` (anchor time and beat, bpm) only when it changes. Each client computes `beatAt(state, clock.serverNow())` every frame. Any new command (seek, setBpm, loop) must be a pure `PlaybackState → PlaybackState` transition in `timeline.ts` that keeps `beatAt` continuous at the switch moment. Per the spec, seeks and BPM changes take effect at the next barline.
- Both sides use `performance.now()` (monotonic). Never use `Date.now()`. A server restart resets its clock: `smoothOffset` jumps instead of blending when the change is >50ms, and clients resync on every reconnect.
- **Timed changes go in `PlaybackState.jump`** `{atServerTime, beat?, bpm}`: from that time on, the position continues from `beat` (a seek; omitted for a tempo-only change) at `bpm`. It is broadcast before it happens, so every device switches together. `change()` in `timeline.ts` puts it on the first barline at least `CHANGE_LEAD_MS` away (bars can differ in length, so commands take a `Barlines` lookup from `barlines(compiled)`, never a beats-per-bar number), or merges into a jump that is already pending. Every transition first `settle`s a jump that has already fired into the anchor. `loop {startBeat, endBeat}` wraps the position. Use `segments(state, from, to)` for anything that needs time ↔ beat over a window (the audio engine does); there is no single inverse of `beatAt`.
- **Start** anchors one count-in bar at `serverNow + 1500ms`, plus a jump to the start bar when the count-in ends, so beats are negative before song start: below −beatsPerBar means waiting, −beatsPerBar to 0 is the count-in (always in the song's own meter). The server starts from `resumeBeat` (the bar it stopped in, or 0 once the song is over). Stop parks at a pending jump's target.
- Room logic is transport-agnostic: `createRoom(code, host)` in `shared/src/room.ts` owns one room's playback state, drum edits and members, and handles `setPart` and `cmd`. The host supplies `now()`, the catalog and an optional `saveSong`. Peers are `{id, send}`. `ping`, `create`, `join`, room codes and expiry belong to the transport, because a Durable Object holds one room while Node holds them all. Test room behaviour directly in `room.test.ts`; test the transport in `server.test.ts`. The room persists through `host.changed()` + `snapshot()`, and `createRoom(code, host, saved)` plus `restore(peer, part)` resume it silently.
- `worker/` is the Cloudflare transport. `src/index.ts` serves `web/dist` as static assets and routes `/ws?room=<code>` or `/ws?create` to one Durable Object per room (`idFromName(code)`; on create, a 409 from the DO means the code is taken, so it retries). `src/roomObject.ts` uses WebSocket Hibernation: member id and part live in each socket's attachment, the room snapshot in DO storage. An alarm reaps sockets quiet for 150s (clients resync their clock every 30s) and wipes the room 10 minutes after it empties. A room is bound to a library on `create`: the message's `key` is looked up in the `LIBRARY_KEYS` secret (`worker/src/libraries.ts`, JSON `{name: key}`, `worker/.dev.vars` locally). No key means the bundled public library (`songs/example-song.json`); a private one loads from R2 `<name>/songs/*.json`. Joining a private room needs the same key, and 5 failed joins a minute rate-limit the room. Keys never go in the socket URL. A private library with an entry in the `LIBRARY_GITHUB` secret (`{name: {repo, token}}`) saves by committing to that repo through the Contents API, refusing with `save-conflict` when git's blob sha differs from the text the room loaded, then writes R2 and bumps `<name>/version`. Rooms notice a new `version` etag on their minute alarm, and on waking compare it with the stored `catalogVersion`, then call `room.catalogChanged()`. Saves carry an optional device name (`saveSong {device}`) that goes into the commit message. `worker/src/libraries.test.ts` covers this against a fake bucket and fake GitHub. `worker/scripts/sync-library.mjs` uploads a library checkout to R2 (local by default, `--remote` for Cloudflare).
- `server/src/server.ts` (`startServer`) is the Node `ws` transport and keeps every room in memory. Empty rooms linger for 10 minutes so reloading phones can rejoin. A ping heartbeat reaps sleeping phones. The `latencyMs` option injects per-message delay in both directions for the simulation test, kept FIFO per connection.
- `web/src/connection.ts` (`RoomConnection`) owns one socket and reconnects, rejoining by room code. It feeds React through `useSyncExternalStore`. The `Room` component creates it in an effect, so StrictMode double-mounts are safe.
- Songs live in `songs/*.json`. The server loads them at startup (`SONGS_DIR` overrides the location), refuses to start on an invalid file, and sends the whole catalog to each client on join. The web app never bundles songs. A beat is what `bpm` counts: `meter(timeSignature)` gives the denominator's note, or a dotted quarter in compound meters (12/8 is 4 beats). A single bar can be written `{ chords, timeSignature }` to change meter, so `compileSong` lays bars out one by one (`BarSpan.startBeat/beats/meter`, `SectionSpan.endBeat`); never assume `barIndex * beatsPerBar`. Use `barIndexAt` to find a bar.
- The protocol goes slightly beyond the spec: `create {part}` (the server generates the code), `cmd selectSong {songId}` (stops and resets to the song's tempo), plus server-to-client `welcome {room, memberId}`, `songs {songs}` and `error {code}`. It also adds:
  - `cmd repeatSection {sectionIndex}` ("再绕一遍"): adds to `PlaybackState.extraPasses`, which is part of the timeline because it moves every later bar. It is refused within `REPEAT_MARGIN_BEATS` of the section's end, and while looping (`looping`). Starting from the top clears it.
  - M3: `cmd seek {sectionIndex, bar}` (bar is 0-based within the section; leaving the loop ends it), `cmd setBpm {bpm}` (integer, `MIN_BPM`–`MAX_BPM`), and `cmd setLoop {sectionIndex | null}`. The spec's `seekSection` became `seek`, so it can also do "从第 X 小节".
  - `setPart {part}`: switches a member's part in place. The web `Room` keeps its connection across part changes.
  - `cmd setDrums` / `cmd setDrumsAll`: room-level drum edits. A section edit of `'default'` drops that section's own pattern so it follows the whole-song default. Edits are broadcast as `edits {songId, drums}` and cleared on song change. Clients compile `applyDrumEdits(song, edits)`.
  - `cmd saveSong`: calls `library.save(songId, raw => applyDrumEdits(raw, drums))`, then re-broadcasts `songs`. A library without `save` is read-only and the save fails.
- `startServer` takes a `SongLibrary` (`shared/src/library.ts`: `list()` plus optional `save(songId, edit)`), never files. `save` takes an edit of the raw JSON so the library can keep `loop` notation, layout and unknown fields; it validates with `parseSong` before storing. `fsLibrary` in `server/src/songs.ts` writes files atomically in `formatJson` style; tests use `memoryLibrary` from `shared`. A relative `SONGS_DIR` resolves against `INIT_CWD` (where npm was started), not `server/`.
- `web/src/ScoreView.tsx` re-renders every animation frame and derives everything from the current beat. Keep it free of local counters and timers. Its `LoopView` (the spec's default loop view) shows one pass of the section as bar cards. It computes the pass from the bar in the section, `floor(barInSection / loopBars)`, and previews the next section on the last pass.
- Settings and editors open in `Sheet` overlays, never inline, because the room layout fills the screen and inline panels overlap the score in portrait.

## Everything follows the sync clock

Anything that moves in time is a function of `beatAt(state, clock.serverNow())`, never a clock of its own:

- **Audio (M2.5):** sounds are events at beat positions. `shared/src/sound.ts` (`soundEvents`) derives metronome, count-in, drum-pattern and fill events for a beat window as a pure function. `web/src/audio/engine.ts` (`AudioEngine`) wakes every 25ms and schedules the next 100ms on the AudioContext clock, never firing sounds from timers. It maps performance time to audio time at the speaker with `getOutputTimestamp()`, which already includes output latency (the fallback subtracts `outputLatency`). The lookahead window starts at the output latency, so events reach the audio thread about 100ms early. While the page is hidden or the phone is locked, timers are throttled to about 1s, so it queues 3s ahead instead. It applies a per-device ±300ms compensation slider for Bluetooth, and drops and reschedules its queue on any playback, song or sound-setting change. Sound settings are per device (localStorage `onbeat.sound`). Drum patterns are `x`/`X`/`.` step strings, `stepsPerBar(meter)` long (sixteenths; eighths in compound meters), in the `drums` part. A bar of a different length plays the start of the pattern, or starts it over. The kit WAVs in `web/public/kits/default/` come from `tools/gen-kit.mjs`.
- **alphaTab (deferred, M4.5 at the earliest):** an optional Guitar Pro / MusicXML layer on top of the JSON skeleton, rendering only the user's track. Never use alphaTab's player timing. Set its cursor every frame from our position, and map beat → bar using the playback order with repeats unrolled.
- The JSON skeleton (sections, bars, chords, strums) is the only layer sync depends on.

## Constraints from the spec

- Lyrics are an optional song field (personal project, local use).
- The scale-degree (级数谱) section of the spec is a proposal: **confirm the design with the user before implementing any of it**, including degree-based chord storage, key changes and cues.
- Out of MVP scope: accounts, audio backing tracks, native apps. No DB and no login. Songs are JSON in the repo.
- Record third-party dependency licenses (alphaTab etc.) in `README.md`.
- The UI is in Chinese and uses large type, readable from about 1m. It must work in both portrait and landscape.
- On iOS Safari, audio unlock needs a tap and Wake Lock needs HTTPS. Both must be verified on a real device.
- Work one milestone at a time. At the end of each, stop so the user can test on phones, and update `README.md` with how to run locally and open on a phone.
